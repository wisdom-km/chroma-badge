## 3. 按依赖顺序执行，不按日历许诺

### 阶段 A：让错误可见、可停止

工作包 A1：F01/F02/F09，范围限固件启动、睡眠、自检错误表达。先固定本轮可构建依赖，保留 `v0.1` 原二进制作基线，新增修订版本号。不要在此包同时实现 FTM、BLE、UI。

工作包 A2：F04/F18/F19，范围限检查与导出门禁。每个检查都必须有当前输出、返回码与输入指纹。先测试 fail，再测试 pass。全量 warning 不能默认吞掉；按类型、对象、理由、批准人和失效条件登记豁免。检查失败只产生诊断报告，不产生看似可下单的包。

A1/A2完成后才把状态从“缺陷已确认”改为“已修复并测试”。本轮新增的 probes 是诊断工具，部分断言要求旧缺陷确实复现；修复后应转换为防回归期望，不能靠继续通过旧缺陷断言验收新版本。

### 阶段 B：关闭硬件待决项

提交给 Wisdom 的讨论材料应包含：J1.7 两种处理方式及影响；LDO 与升压候选BOM、有效容值和电流依据；电池充电约束；网络规则变化；USB模型及公差来源。先做这些材料，最后才请求批准具体改动。保持四色屏、ESP32-C3、ST25DV、电池+USB、0.8 mm 主架构。

若批准网络/铜皮改变：从 `design.py` 出发，明确是否必须重建板。重建前另存当前布线版本及hash；Freerouting仍严格遵循原交接第3节。若只是文档、阻焊、显示错误修复，不清走线。每次后处理之后再次检查设计网络、原理图网络和PCB焊盘，而不是只看DRC。

### 阶段 C：工程样机闭环

按“电源 → MCU启动/下载 → I²C身份与事件 → 供电/显示 → 深睡唤醒 → 图像传输 → 整机功耗/RF → 装配”的顺序带板。任何一步失败留日志，不继续宣称后续通过。建议先做3块带编号样机，以区分个体焊接问题与系统问题；数量是建议，不是已批准采购。

### 阶段 D：产品功能与维护

只选择一条首版手机传图路线；建立所有权/写入授权窗口、完整性与异常恢复后做姓名、组织、二维码、四色模板。没有目标机型实测不能标“支持iPhone/Android”。批量发布再做治具、离线配置、返修与许可清单。
